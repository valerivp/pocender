# Техническое задание
## CNC Client — модификации интерфейса и интеграция с Hub

**Версия:** 1.0  
**Дата:** 13.09.2026  
**Статус:** рабочее ТЗ

---

## 1. Назначение документа

Настоящее техническое задание описывает **только модификации**, которые необходимо внести в CNC Client относительно существующей реализации/спецификации интерфейса POCENDER.

Полное описание базового интерфейса POCENDER в настоящее ТЗ не копируется. Оно является отдельным документом и должно рассматриваться как нормативная часть требований к Client:

**[POCENDER UI Formal Specification v0.2](pocender_ui_formal_spec_v0.2.md)**

При реализации необходимо использовать указанную спецификацию как основной документ по существующим экранам, элементам, геометрии, состояниям и поведению.

Цель проекта — максимально воспроизвести интерфейс и функциональность POCENDER, не изменяя существующее поведение без отдельного требования.

---

## 2. Граница настоящего ТЗ

Настоящее ТЗ определяет только две новые функции Client:

1. страницу управления Hub;
2. универсальный режим контекстной справки по кнопкам и полям.

Внутренняя архитектура Hub, его серверная реализация, драйверы COM/USB, маршрутизация, очереди, хранение данных и прочие внутренние механизмы Hub **не входят в настоящее ТЗ**.

Client взаимодействует с Hub только через внешний интерфейс, предоставляемый Hub.

---

## 3. Общие требования к Client

### 3.1. Сохранение существующего интерфейса

Все существующие страницы и функции POCENDER должны продолжить работать согласно отдельной спецификации интерфейса.

Новые функции не должны самопроизвольно изменять:

- геометрию существующих экранов;
- названия существующих элементов;
- порядок навигации;
- существующие действия;
- существующие состояния;
- существующую логику управления станком.

### 3.2. Работа с прямым портом и Hub

Client должен поддерживать два варианта подключения к станку:

**Прямое подключение**
```text
Client → COM/USB → CNC controller
CNC controller → COM/USB → Client
```

**Подключение через Hub**
```text
Client → G-code WebSocket → Hub → COM/USB → CNC controller
CNC controller → Hub → G-code WebSocket → Client
```

Для основной CNC-логики оба варианта должны предоставлять одинаковый поток G-code/ответов контроллера.

Управление Hub является отдельной функцией и доступно только при наличии подключения к Hub.

---

# 4. Страница управления Hub

## 4.1. Назначение

Необходимо разработать новую страницу Client для управления и мониторинга Hub.

Страница предназначена для:

- отображения входных источников Hub;
- отображения выходного канала;
- выбора режима передачи каждого входа;
- просмотра текущего потока данных;
- настройки источников;
- перехода к подробному просмотру журнала;
- управления селектором источников.

---

# 5. Геометрия страницы Hub

## 5.1. Логическая сетка

Для страницы используется существующая логическая модель экрана POCENDER:

- 10 логических строк по вертикали;
- вертикальные координаты и размеры элементов задаются целыми строками;
- дробные значения `y` и `h` запрещены;
- горизонтальные координаты и размеры задаются в процентах ширины экрана.

## 5.2. Деление экрана

Экран делится по вертикали на **5 равных логических блоков**:

```text
┌──────────────────────────────┐
│ INPUT 1                       │
├──────────────────────────────┤
│ INPUT 2                       │
├──────────────────────────────┤
│ INPUT 3                       │
├──────────────────────────────┤
│ INPUT 4                       │
├──────────────────────────────┤
│ OUTPUT                        │
└──────────────────────────────┘
```

При наличии 10 логических строк каждый блок занимает 2 строки:

```text
Input 1: y=0, h=2
Input 2: y=2, h=2
Input 3: y=4, h=2
Input 4: y=6, h=2
Output:  y=8, h=2
```

---

# 6. Блок входа

Каждый из четырёх входных блоков имеет одинаковую структуру.

## 6.1. Состав

Блок должен содержать:

1. название источника;
2. кнопку настройки;
3. кнопку `EXC`;
4. кнопку `ADD` либо `MUTE`;
5. окно текущего логирования;
6. состояние соединения/источника.

## 6.2. Горизонтальное разделение

Каждый блок делится по ширине на две части:

```text
┌──────────────────────┬──────────────────────────┐
│  управление входом  │       окно логирования   │
└──────────────────────┴──────────────────────────┘
```

Левая половина блока предназначена для управления входом.

Правая половина предназначена для отображения журнала.

Обе части занимают приблизительно по 50% ширины блока.

Точная внутренняя раскладка элементов должна быть выполнена в стиле POCENDER.

---

# 7. Название источника

В левой половине входного блока должно отображаться имя источника.

Имя является пользовательским названием источника и не обязано совпадать с физическим именем COM-порта или IP-адресом.

---

# 8. Кнопка настройки источника

Для каждого входа должна присутствовать кнопка настройки.

Нажатие открывает настройки конкретного входа.

Настройки должны содержать минимум два поля:

1. **Название источника**
2. **Источник**

### 8.1. Название источника

Текстовое поле. Используется для отображения источника на странице Hub.

### 8.2. Источник

Должна быть возможность выбрать:

- COM/USB-порт;
- WebSocket текущего компьютера;
- WebSocket по указанному IP-адресу.

Для локальных портов используются обнаруженные системой устройства.

Для удалённого WebSocket пользователь должен иметь возможность указать IP-адрес.

Конкретный формат адреса и остальные параметры подключения определяются внешним протоколом Hub.

---

# 9. Режим EXC

Для каждого входа должна существовать кнопка:

```text
EXC
```

`EXC` означает **Exclusive**.

При активации `EXC`:

- выбранный источник становится активным;
- остальные клиенты/входы отключаются от передачи в выходной поток;
- поток выбранного источника направляется в станок;
- состояние остальных входов отображается согласно состоянию Hub.

EXC является взаимоисключающим режимом относительно других источников.

---

# 10. Режим ADD

Для каждого входа должна существовать кнопка:

```text
ADD
```

`ADD` означает добавление потока этого источника к потоку, направляемому в станок.

При включении ADD:

- источник становится активным;
- команды от данного источника добавляются в выходной поток;
- остальные активные источники не отключаются;
- одновременно могут быть активны несколько источников.

После включения режима ADD надпись на кнопке должна измениться:

```text
ADD → MUTE
```

---

# 11. Режим MUTE

После включения ADD кнопка должна отображаться как:

```text
MUTE
```

Нажатие `MUTE` отключает передачу команд данного источника в выходной поток.

MUTE **не означает обязательный разрыв соединения с источником**.

Источник может продолжать:

- оставаться подключённым;
- передавать данные;
- отображаться в журнале;
- быть доступным для повторной активации.

После отключения режима MUTE кнопка снова отображается как:

```text
ADD
```

---

# 12. Взаимодействие EXC / ADD / MUTE

Для каждого входа допускаются состояния:

```text
неактивен
    │
    ├── EXC ──► эксклюзивный активный
    │
    └── ADD ──► добавочный активный
                     │
                     ▼
                   MUTE
                     │
                     ▼
                  неактивен
```

При включении `EXC` все остальные источники должны быть исключены из выходного потока.

При включении `ADD` остальные источники не отключаются.

Фактическое состояние должно определяться Hub.

---

# 13. Окно логирования входа

Правая половина каждого входного блока содержит окно логирования.

Высота отображаемого журнала — **2 логические строки**.

Окно предназначено для отображения последних поступивших данных источника.

Client не должен изменять G-code только ради его отображения.

---

# 14. Просмотр полного журнала

Нажатие на окно логирования должно открывать отдельный экран просмотра журнала конкретного источника.

Экран должен отображать **последние 1000 строк**.

Необходимо:

- хранить в Client историю до 1000 строк для отображения;
- отображать строки в порядке поступления;
- обеспечить просмотр последних данных;
- обеспечить возврат на страницу Hub;
- явно указывать источник журнала.

1000 строк является ограничением пользовательского интерфейса Client. Это не является требованием к внутреннему хранилищу Hub.

---

# 15. Блок OUTPUT

Пятый блок страницы предназначен для выходного канала.

```text
┌────────────────────────────────┐
│ OUTPUT                         │
│                                │
│              LOG               │
│                                │
└────────────────────────────────┘
```

Блок должен иметь:

- название выходного канала;
- состояние подключения/выхода;
- окно логирования;
- кнопку настройки, если она предусмотрена внешним интерфейсом Hub.

Выходной блок не имеет EXC/ADD/MUTE.

## 15.1. Лог выхода

Окно логирования выхода должно отображать поток данных выходного канала согласно данным Hub.

Нажатие на окно открывает просмотр последних 1000 строк аналогично входным журналам.

---

# 16. Страница просмотра журнала

Для входного и выходного журнала используется единый тип экрана.

Экран должен:

- отображать название источника/выхода;
- отображать до 1000 последних строк;
- позволять просматривать журнал;
- иметь кнопку возврата;
- сохранять визуальный стиль POCENDER.

Если содержимое строки длиннее доступной ширины, способ отображения должен обеспечивать просмотр полного содержимого строки без изменения самого содержимого.

---

# 17. Страница настройки источника

Для настройки входа необходимо создать отдельный экран/диалог в стиле POCENDER.

Минимальный набор:

```text
Название источника
[________________]

Источник
[________________]

[ OK ] [ CANCEL ]
```

Тип источника должен позволять выбрать:

```text
COM / USB
Local WebSocket
Remote WebSocket
```

Для Remote WebSocket необходимо поле адреса/IP.

Для COM/USB должны быть доступны обнаруженные системой устройства.

---

# 18. Количество входов

Количество отображаемых входов на странице Hub фиксируется равным:

```text
4
```

Это ограничение относится к пользовательскому интерфейсу Client.

Причина ограничения — экран содержит 10 логических строк и разделён на пять блоков по две строки.

Hub может технически поддерживать большее количество источников, однако Client в рамках данной страницы отображает максимум четыре входа.

---

# 19. Управление Hub через WebSocket

Страница Hub должна работать через отдельный **Control WebSocket**.

G-code WebSocket и Control WebSocket являются разными соединениями.

## 19.1. G-code WebSocket

Используется исключительно для CNC-потока:

```text
Client → Hub → CNC
CNC → Hub → Client
```

В этом потоке не должно быть управляющих сообщений Hub.

## 19.2. Control WebSocket

Используется для:

- управления селектором;
- настройки источников;
- получения состояния источников;
- получения информации о подключениях;
- получения данных журналирования остальных портов;
- получения состояния выходного канала.

Конкретный формат сообщений определяется внешним протоколом Hub и не должен дублироваться в UI-спецификации.

---

# 20. Прямое подключение без Hub

Если Client подключён непосредственно к COM/USB станка, страница управления Hub не должна пытаться имитировать существование Hub.

В этом режиме:

- CNC-поток работает напрямую;
- Control WebSocket отсутствует;
- функции управления Hub недоступны;
- selector Hub отсутствует;
- источники Hub отсутствуют.

Основной CNC-интерфейс POCENDER продолжает работать.

---

# 21. Определение режима подключения

Client должен различать:

```text
DIRECT
HUB
```

На основании фактически установленного транспорта.

Не требуется анализировать содержимое G-code для определения наличия Hub.

Если используется прямой Serial/USB Transport:

```text
mode = DIRECT
```

Если используется Hub G-code WebSocket совместно с Control WebSocket:

```text
mode = HUB
```

В режиме HUB становятся доступны функции Hub UI.

---

# 22. Контекстная справка `?`

На каждой странице Client должна присутствовать кнопка:

```text
?
```

Кнопка должна быть доступна независимо от текущей страницы, если геометрия конкретного экрана допускает её размещение без нарушения существующего интерфейса POCENDER.

---

# 23. Режим справки

После нажатия `?` Client переходит в режим получения справки.

Основное правило:

> После включения режима справки нажатие на любую кнопку или поле должно не выполнять действие, а показать пользователю подсказку об этом элементе.

То есть:

```text
обычный режим:
нажатие элемента → действие

режим ?:
нажатие элемента → описание элемента
```

---

# 24. Поведение режима справки

После включения режима `?`:

1. Client визуально показывает, что активен режим справки.
2. Пользователь нажимает любую кнопку, поле или другой интерактивный элемент.
3. Обычное действие элемента НЕ выполняется.
4. Отображается описание назначения элемента.
5. Режим справки остаётся активным, позволяя последовательно выбирать разные элементы.
6. Пользователь может получить описание любого доступного элемента.

Цель — изучение интерфейса без риска случайного выполнения действия.

---

# 25. Источник текста подсказки

Для каждого интерактивного элемента должна существовать текстовая запись описания.

Для существующих элементов в первую очередь используется описание из формализованной спецификации POCENDER.

Для новых элементов Hub описание определяется настоящим ТЗ либо отдельным дополнением к спецификации интерфейса.

Не следует автоматически генерировать техническое описание только из имени элемента.

---

# 26. Справка для полей

В режиме `?` нажатие на:

- числовое поле;
- текстовое поле;
- выпадающий список;
- координатное поле;
- поле настройки;

не должно переводить поле в режим редактирования.

Вместо этого показывается подсказка:

- назначение поля;
- его смысл;
- при необходимости допустимые значения;
- влияние значения на работу функции.

---

# 27. Справка для кнопок

Для кнопок необходимо отображать:

- название;
- назначение;
- эффект нажатия;
- при необходимости условия доступности;
- при необходимости различия короткого нажатия и удержания.

Если кнопка имеет алгоритм удержания, справка должна описывать это поведение.

---

# 28. Безопасность режима справки

В режиме `?` не должны выполняться опасные действия.

В частности, нажатие на:

- RESET;
- END;
- HOME;
- ZERO;
- GOTO;
- RUN;
- SPINDLE;
- COOLANT;
- JOG-кнопки;
- EXC;
- ADD;
- MUTE;

должно только показать справку.

Это обязательное требование.

---

# 29. Выход из режима справки

Должна существовать возможность вернуться в обычный режим.

Поведение кнопки `?` в активном режиме:

```text
? OFF → включить режим справки
? ON  → выключить режим справки
```

---

# 30. Визуальное состояние режима справки

Активный режим `?` должен визуально отличаться от обычного режима.

При этом нельзя изменять существующую геометрию экрана больше необходимого.

Рекомендуется использовать существующую визуальную систему состояний POCENDER.

---

# 31. Архитектурные требования к реализации

## 31.1. UI не должен напрямую работать с транспортом

Экран Hub должен взаимодействовать с абстракцией Hub Control Client:

```text
Hub UI
  ↓
Hub Control API
  ↓
Control WebSocket
```

Основной CNC интерфейс:

```text
POCENDER UI
  ↓
CNC Transport
  ├── Serial Transport
  └── WebSocket Transport
```

## 31.2. Независимость от транспорта

Основные экраны POCENDER не должны содержать отдельную реализацию каждой команды для COM и WebSocket.

Различие транспорта должно быть скрыто соответствующим уровнем абстракции.

---

# 32. Работа журналирования

Client должен поддерживать отдельные логические буферы:

```text
Input 1 log
Input 2 log
Input 3 log
Input 4 log
Output log
```

Каждый буфер:

- сохраняет строки в порядке поступления;
- ограничивается последними 1000 строками;
- используется как для краткого отображения, так и для страницы полного просмотра.

Краткое окно показывает последние данные, помещающиеся в две строки.

---

# 33. Требования к данным журнала

Журнал не должен использоваться для изменения или повторной генерации G-code.

Если Hub передал:

```text
G1 X10 Y20 F500
```

в журнале должна отображаться эта команда, насколько это позволяет представление строки.

Не допускается автоматическое форматирование, округление координат или изменение регистра как часть логики журналирования.

---

# 34. Обработка потери Control WebSocket

Если Control WebSocket разорван:

- Client должен отобразить недоступность Hub Control;
- состояние, требующее подтверждения от Hub, не должно считаться достоверным;
- UI не должен самостоятельно объявлять источник активным только на основании предыдущего состояния;
- основной G-code канал обрабатывается независимо, согласно состоянию его собственного соединения.

---

# 35. Обработка потери отдельного источника

Если Hub сообщает, что источник отключён:

- источник отображается как отключённый;
- его журнал не исчезает;
- последние данные остаются доступными для просмотра;
- EXC/ADD/MUTE не должны отображаться как активные, если Hub сообщает, что источник больше не участвует в соответствующем режиме.

---

# 36. Состояние UI должно соответствовать Hub

Client не должен самостоятельно поддерживать альтернативную модель состояния selector.

После выполнения:

```text
EXC
ADD
MUTE
```

Client отправляет операцию Hub и отображает подтверждённое состояние.

Если Hub вернул ошибку, Client должен показать ошибку и не переводить кнопку в подтверждённое активное состояние.

---

# 37. Нормативные требования настоящего ТЗ

Нормативными являются:

1. страница управления Hub;
2. четыре входных блока;
3. один выходной блок;
4. 10 логических строк;
5. пять блоков по две строки;
6. EXC;
7. ADD;
8. MUTE;
9. настройка имени и источника;
10. поддержка COM/USB, локального WebSocket и удалённого WebSocket/IP;
11. краткий журнал высотой две строки;
12. просмотр последних 1000 строк;
13. отдельный Control WebSocket;
14. отдельный G-code WebSocket;
15. кнопка `?`;
16. режим справки без выполнения действий;
17. работа Client напрямую с COM/USB без Hub.

---

# 38. Что не входит в настоящее ТЗ

Не проектируются:

- внутреннее устройство Hub;
- реализация serial-драйверов Hub;
- алгоритм очереди команд Hub;
- внутренняя реализация selector;
- хранение журналов на Hub;
- серверная база данных;
- авторизация Hub;
- удалённое администрирование Hub;
- внутренний формат файлов Hub;
- изменение GRBL;
- новый CNC-протокол вместо G-code;
- redesign существующего интерфейса POCENDER.

Эти вопросы должны быть описаны в отдельном ТЗ Hub.

# 39. Критерии приёмки

### Hub UI

- на экране отображаются четыре входа и один выход;
- экран использует 10 логических строк;
- каждый блок занимает две строки;
- каждый вход имеет EXC и ADD;
- после ADD кнопка становится MUTE;
- EXC отключает остальные источники согласно состоянию Hub;
- ADD позволяет одновременно использовать несколько источников;
- каждый вход имеет настройку;
- настройка содержит имя и источник;
- поддерживаются COM/USB, local WebSocket и remote WebSocket/IP;
- каждый вход имеет окно журнала высотой две строки;
- нажатие на журнал открывает просмотр последних 1000 строк;
- выход имеет собственный блок и журнал.

### Транспорт

- G-code передаётся отдельным WebSocket;
- управление Hub передаётся отдельным Control WebSocket;
- CNC-поток не содержит управляющих сообщений Hub;
- прямое COM/USB подключение продолжает работать без Hub;
- интерфейс CNC не зависит от конкретного транспорта.

### Справка

- кнопка `?` доступна на каждой странице;
- включение режима `?` не выполняет CNC-команд;
- нажатие любого интерактивного элемента показывает его описание;
- опасные операции в режиме справки не выполняются;
- режим можно отключить.

### Совместимость с POCENDER

- существующие страницы не изменяются без необходимости;
- существующие элементы продолжают работать согласно отдельной спецификации;
- визуальный стиль новых элементов соответствует POCENDER;
- новые функции не заменяют существующую модель интерфейса.
